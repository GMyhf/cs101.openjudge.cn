## 1. 部署与发版

服务由 systemd 托管，单元文件在 `deploy/cs101.service`（已入库）。

### 首次安装

```bash
sudo cp deploy/cs101.service /etc/systemd/system/cs101.service
sudo systemctl daemon-reload
sudo systemctl enable --now cs101
```

换机器只需改单元里的 `User` / `Group` / `WorkingDirectory` 三行。

### 发版

```bash
tools/release.sh
```

**就这一条。** 它做四件事：拉代码 → 单元有变化就同步并 `daemon-reload` → 重启 →
等健康后**跑一遍全语言冒烟**。任何一步失败就退出非零。

冒烟绑在发版里是有原因的：改用 systemd 托管那次，**代码一行没动，PyPy3 却静默失效了** ——
systemd 不继承登录 shell 的 PATH，判题器再也找不到 `~/.local/bin/pypy3`。
**换部署方式会悄悄改变判题器能看见什么**，而单元测试在开发机上跑，看不见这件事。

只想重启不想跑冒烟时才用 `sudo systemctl restart cs101`。
不要再用 `pkill` + `nohup` 手工重启，原因见 §7 排障。

### 什么时候必须跑冒烟

除了每次发版，以下情况也要（都属于「代码没变但能力可能变了」）：

- 改过 systemd 单元
- 换机器、重装系统
- 装卸任何工具链（python / pypy3 / gcc / dotnet / swiftc / clang）

### 日常命令

```bash
systemctl status cs101          # 状态
journalctl -u cs101 -f          # 实时日志
journalctl -u cs101 --since today
```

> Python **不会热加载**。`git pull` 之后不重启，改动不会生效 —— 但
> `index.html`/`problems.html`/`history.html`/`admin.html` 是从磁盘现读的，
> 拉下来就变了。这两者混在一起最容易误判「已经上线了」，务必以 `systemctl restart` 为准。

## 3. 管理页 `/admin/`

只有管理员可见（导航里的「判题设置」入口对其他人隐藏，接口层面也会 403）。

### 出错输入片段开关

控制 WA 时是否把**出错那组的输入**下发给学生。三层，从严到宽：

```
考试时段内 → 一律关闭（一票否决）
     ↓ 否则
按题库覆盖 → 该题库单独设定
     ↓ 否则
全局默认开关
```

时段只会让结果更严，永远不会意外放开。**开关关闭时片段根本不进接口返回**，是服务端不下发，不是前端藏起来。

### 频次限额

四个端点的次数与窗口都可在线调整，**改完立即生效、不用重启**：

| 端点 | 默认 | 计数依据 |
| --- | --- | --- |
| `/api/run` 运行样例 | 30 次 / 5 分钟 | 用户名 |
| `/api/submit` 提交判题 | 20 次 / 10 分钟 | 用户名 |
| `/api/user/register` 注册 | 100 次 / 10 分钟 | 来源地址 |
| `/api/user/forgot` 找回密码 | 10 次 / 10 分钟 | 邮箱 + 来源地址 |

**次数填 0 表示不限。**

> **考试当天**：学生提交会比平时密集得多。撞上限额时把 submit 调大或填 0，考完再调回来。
> 这正是把它做成在线可调的原因 —— 需要放宽的时刻恰恰最不能重启。

> ⚠️ **注册和找回密码按来源地址计数**，而一个班常在同一出口 IP 后面。
> 开学第一节课集中注册可能撞上 100 次/10 分钟。如果班级规模大，**提前调大或临时填 0**。
> 这不是理论顾虑：加这条限制时整个测试套件立刻变红，因为 46 个用例全从同一地址注册。

限额与出错片段开关都存在 `settings` 表里，重启不丢。

## 4. 判题沙箱（红线，改动前务必读）

用户代码是不可信的。`judge.py` 的 `_limits()` 是唯一的防线：

| 限制 | 值 |
| --- | --- |
| `RLIMIT_CPU` | 单组 CPU 秒数，夹在 4 ～ 20 秒 |
| `RLIMIT_AS` | 768 MB（.NET 系 1536 MB） |
| `RLIMIT_FSIZE` | 2 MB（.NET 系 16 MB） |
| 子进程 `env` | **恰好** `{PATH, HOME}`，`PATH` 固定为 `/usr/local/bin:/usr/bin:/bin` |
| Python | 带 `-I`（隔离模式） |
| 工作目录 | 每次判题一个临时目录，判完即删 |

整次提交墙钟预算 = 题面总限时 × 语言倍率，下限「组数 × 4 秒」，**硬顶 300 秒**。

**这些不是建议，是有机械判据的契约。** `tests/test_judge.py` 的 `SandboxContractTests`
会逐项断言，并且验证**每一条执行路径**（判题与运行样例）都真的经过 `_limits`。
任何放宽都会让它变红 —— 这是刻意的。改之前先问：能不能不放宽？

> 历史教训：加 PyPy3 时先测了「不放宽能不能跑」，答案是能，于是没有放宽。
> **先测能不能不放宽，再决定要不要放宽。**

## 5. 数据与题库

```
data/openjudge/
  catalog.json          题库索引（4.1 MB）
  limits.json           每题限时
  pages/                题面镜像 book__id.html
  tests/<桶>/<题号>_made/  测试数据（*.in / *.out）
```

- 重新抓取题面目录：`python3 scripts/crawl_openjudge.py`
- 重扫测试数据并重建索引：`python3 scripts/index_tests.py`

**放了新数据一定要重建索引**，否则那些题在站点上仍显示「无测试数据」，
本地判题也看不到它们。

当前 1849 道题中 1846 道有数据。未覆盖的 3 道属结构性不可做：
`00000`（输出约 20 MB，超判题器上限）、`03259`（题面无样例）、`29986`（交互题）。

### 备份

要备份的是 **`data/course.db`**（账号、口令哈希、全部提交记录）和两个配置文件。
题库数据可以从仓库和抓取脚本重建，数据库不能。

由 `cs101-backup.timer` 每天自动跑（关机错过会补跑）：

```bash
sudo cp deploy/cs101-backup.{service,timer} /etc/systemd/system/
sudo cp deploy/cs101-alert@.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now cs101-backup.timer
```

日常：

```bash
python3 tools/backup_db.py --list                       # 有哪些备份
python3 tools/backup_db.py --verify <文件>               # 单独验一份
python3 tools/backup_db.py --restore <文件> --to /tmp/x.db   # 还原到别处再自行替换
systemctl list-timers cs101-backup.timer                # 下次什么时候跑
journalctl -u cs101-backup --since '7 days ago'         # 近期备份记录
```

备份用 SQLite 在线备份 API（不是 `cp`，服务在跑时 `cp` 可能拷到写了一半的库），
落盘前对**备份文件本身**跑 `integrity_check` 并与源库核对行数，权限 `600`，
默认保留 14 份，存在 `~/backups/cs101`（仓库之外 —— 里面有口令哈希）。

#### 异地备份

本地轮转只防误删、改坏、损坏，**不防这台机器没了** —— 备份和数据库在同一块盘上。
在 `cs101-backup.service` 里设目标即可开启：

```ini
Environment=CS101_BACKUP_REMOTE=用户名@100.76.69.33:~/cs101-backups
```

前置：本机 `~/.ssh/id_ed25519.pub` 要进到目标机的 `~/.ssh/authorized_keys`，
且目标机开着「远程登录」。改完 `daemon-reload` 再跑一次 `cs101-backup.service` 验证。

推送不是「rsync 退出 0 就算数」：推完会**回读远端那份的 sha256 和本地比对**，
不一致就非零退出（触发告警）。只看退出码等于没验 —— 一份从没验过的异地备份只是一个假设。

异地失败**不会**丢掉本地那份：本地已经落盘，失败只影响退出码。

> 留空 `CS101_BACKUP_REMOTE` 时，每次备份都会打印一行提醒「这台机器没了备份也一起没」。

### 服务失败告警

`cs101.service` 与 `cs101-backup.service` 都带 `OnFailure=cs101-alert@%n.service`。
`Restart=on-failure` 会把服务自动拉起来 —— 好事，但也让**崩溃循环变成静默的**，
自动恢复不该等于无人知晓。告警复用 `data/.smtp.env` 的邮件配置，
收件人取 `CS101_ALERT_EMAIL`（未设则退回 `CS101_SMTP_FROM`）。
邮件发不出去也会在 journal 里留记录，且不会让告警单元自己失败。

## 6. 安全边界

以下都是已经加固过的地方，改动时不要退回去：

**静态文件白名单。** 只分发首页和 `static/` 下的白名单后缀。
早先是「ROOT 下的文件都发」，实测 `GET /data/course.db` 能下到整个数据库
（口令哈希 + 全部提交），`data/.admin_password` 走同一条路径。
`.gitignore` 挡的是 git，不是 HTTP。

**口令哈希。** PBKDF2-SHA256，12 万轮，**每用户随机盐**。
老格式（全库共用一个写在源码里的盐）仍能登录，并在下次成功登录时自动升级。

**会话。** 最长 14 天；改密码或重置密码会吊销该用户的其它会话。
登录连续失败 10 次锁 15 分钟（按用户名，不按 IP —— 按 IP 会锁掉整个班）。

**找回密码不泄露注册情况。** 无论邮箱是否存在，响应完全一致；
限频写在查库**之前**，否则「只有真实邮箱会被限住」本身就成了泄露信号。

**`CS101_SHOW_RESET_LINK` 请保持不设。** 设为 `1` 时，未配邮件服务的情况下
重置链接会直接返回给调用者 —— 等于**知道某人邮箱就能接管其账号**。
这个开关只为本机开发存在。生产环境请确保 SMTP 配置正常。

**上游代理不转发凭据。** 未命中本地镜像的 GET 会回源 `cs101.openjudge.cn`，
只带一个 User-Agent，不转发本地 cookie。
注意上游对不存在的路径**自己就返回 200**（软 404），所以针对本站的检查
应当断言响应内容而不是状态码。

## 6.5 公网访问（Tailscale Funnel）

服务本身只监听内网/tailnet。对外开放走 **Tailscale Funnel**：免费、自带 HTTPS 证书、
不用改路由器、不暴露真实 IP、一条命令可关。

```bash
sudo tailscale funnel --bg --https=8443 http://127.0.0.1:8000   # 开
sudo tailscale funnel --https=8443 off                          # 关
tailscale serve status                                          # 看当前配置
```

当前对外地址：**`https://jensen.taildf6cf3.ts.net:8443/`**

> 用 8443 而不是 443，是因为 443 的 `/` 已被本机另一个服务（`localhost:8107`）占用。
> Funnel 只允许 443 / 8443 / 10000 三个端口。

### ⚠️ 反代会打掉按 IP 的限频 —— 换任何代理前都要看这条

**实测**：开 Funnel 后，从公网发来的请求，服务端看到的 `client_address` 是 **`127.0.0.1`**
（代理跑在同一台机器上）。若按它限频，等于**把整个互联网算成一个客户端** ——
一个脚本就能耗尽全局额度、把所有人挡在门外，而它自己反而不受单独限制。

注册与找回密码是仅有的两个**未登录**端点，限频是它们唯一的闸，所以这条必须对。

`server.py · Handler.client_ip` 因此按 `X-Forwarded-For` 取真实地址，
**但只在连接来自 `TRUSTED_PROXIES`（本机）时才采信** —— 否则直连的人加个头
就能伪造自己的 IP。

**换成 nginx / Cloudflare / 其它代理时**，必须确认两件事，否则限频会静默失效：

1. 代理确实设置了 `X-Forwarded-For`
2. 代理到本服务的连接来自 `TRUSTED_PROXIES` 里的地址（不是的话要把它加进去）

验证方法（从**真正的外网**，不能从 tailnet 内，MagicDNS 会把域名解析成内网地址）：

```bash
# 先向公共 DNS 查 Funnel 的公网 IP，再强制走它
curl --resolve jensen.taildf6cf3.ts.net:8443:<公网IP> \
     https://jensen.taildf6cf3.ts.net:8443/probe-test
# 然后看日志里记的是不是你的真实公网 IP
journalctl -u cs101 -n 20 | grep probe-test
```

### 对外开放前必须改的两项

| 项 | 为什么 |
| --- | --- |
| `CS101_PUBLIC_URL`（在 `data/.smtp.env`） | 激活与重置链接用它拼。仍指向内网 IP 的话，**校外学生收到的邮件里是打不开的地址，账号根本激活不了** |
| 会话 cookie 的 `Secure` | 已按请求的 `X-Forwarded-Proto` 自动处理：HTTPS 进来才加，tailnet 内的 HTTP 访问不受影响 |

> `CS101_PUBLIC_URL` 由 `server.py` 启动时从 `data/.smtp.env` 读入，**不在 systemd 环境里**，
> 所以 `/proc/<pid>/environ` 查不到。改完必须重启，并确认重启时间晚于配置修改时间。

### 开放之后意味着什么

**任何人都能注册并在这台机器上执行代码**（当前策略：不限邮箱域名）。
`/api/submit` 与 `/api/run` 都要求登录，所以**挡住注册就挡住了代码执行** ——
反过来说，不挡注册就等于开放算力。沙箱限住单次的 CPU/内存/文件，
判题全局并发闸保证最坏情况是排队而非打垮机器，但都挡不住「注册很多号、每个都在额度内」。

要收紧，最省力的一处是给注册加**邮箱域名白名单**：
`server.py` 注册分支里邮箱格式校验那一行旁边。

日常盯这个（现在能看到真实客户端 IP 了）：

```bash
journalctl -u cs101 -f
journalctl -u cs101 --since today | awk '{print $6}' | sort | uniq -c | sort -rn | head
```

## 7. 排障

**服务起不来，`209/STDOUT`，反复重启。**
SELinux 为 Enforcing 时，systemd 以 `init_t` 打不开 home 目录下的文件。
不要给单元加 `StandardOutput=append:.../server.log`，日志走 journal。
同理**不要加 `ProtectHome`** —— 工作目录就在 `/home` 下，加了直接起不来。

**手工重启「成功了」但代码没变。**
`pgrep -f "python3 -u server.py"` 会匹配到**执行这条命令的 shell 自己**
（命令串里就含这段文字），`kill` 把 shell 一起杀掉，链条断在启动新进程之前，
结果老进程活得好好的。用 `systemctl restart`；非要手工就锚定成
`pkill -f "^python3 -u server\.py$"`。

**怎么确认线上真的是新代码？**
挑一个只在新版本才有的**行为**去验，不要只看 `git rev-parse`。
仓库更新了但进程没换是最常见的误判。

**判题很慢 / 机器负载高。**
判题在 HTTP 线程上直接拉起编译器。同一用户已有互斥（同时只跑一个）和频次限额，
但多个用户仍会并发。`journalctl -u cs101` 看请求量，必要时在管理页收紧限额。

**学生反馈某种语言「Language Unavailable」，但机器上明明装了。**
八成是 **PATH**：systemd 不继承登录 shell 的 PATH。判题器用**服务进程**的 PATH
去找解释器/编译器，装在 `~/.local/bin` 之类地方的（比如 pypy3）服务就看不见。
在单元里用 `Environment=PATH=...` 补上。放宽这里不会扩大沙箱 ——
判题器找到后交给子进程的是绝对路径，子进程的 env 仍是固定的 `CHILD_PATH`。

    # 服务实际拿到的 PATH
    tr '\0' '\n' < /proc/$(systemctl show cs101 -p MainPID --value)/environ | grep ^PATH=

**验证所有语言都还能判。**

    CS101_SMOKE_USER=... CS101_SMOKE_PASSWORD=... \
      python3 scripts/smoke_languages.py --require-all

每种语言各跑一份正确解和一份坏代码，确认拿到正确输出与 `Compile Error`。
**部署机上务必加 `--require-all`** —— 不加的话工具链缺失只会「跳过」，
而单元测试里 .NET/Swift/ObjC 的用例本来就是 `skipUnless`，
两处都静默跳过，就是 PyPy3 那次回归能藏住的原因。

**闸门偶发假红。**
`python3 -m unittest` 极少数情况下 `errors=1`，单独重跑即绿。**根因尚未定位。**
已排除两个假设：管道写满（实测一轮约 14 KiB，只占缓冲区 22%）、
服务端启动等待不足（早已是 30 秒）。连跑 6 轮未复现。

**下次红了请先保住现场**（前两次都是被 `tail` 截掉才查不下去的）：

    python3 -m unittest discover -s tests > /tmp/gate.log 2>&1   # 完整输出
    cp /tmp/cs101-test-server.log /tmp/gate-server.log           # 服务端当时在做什么

测试已改为把服务端日志写到 `/tmp/cs101-test-server.log`（固定路径，跑完仍在）。

**不要因为「它有时会抽风」就忽略红色** —— 历史上有过闸门连红四个提交无人察觉。
重跑一次确认，仍红就是真红。

## 8. 开发与协作

### 交接闸门

任何改动交付前必须通过：

```bash
python3 tools/handoff.py --verify
```

它跑全套单元测试、`py_compile`、跨批次返工检查和全库横扫。**退出码 0 才算过。**

### 协作脚手架

`collab/` 是 Claude 与 Codex 的共享事实源：

| 文件 | 作用 |
| --- | --- |
| `PLAN.md` | 唯一任务清单 + 决策记录（人拍板，agent 认领并更新状态） |
| `HANDOFF.md` | 每次「我做完了，轮到你」的交接记录 |
| `NOTES-claude.md` / `NOTES-codex.md` | 双方留给对方的话 |

生成 review 包交给另一方：

```bash
python3 tools/handoff.py --from claude --to codex --verify
```

### 这个项目的几条经验

- **标准立了但没有机械判据，等于没立。** 沙箱契约、样例解析前提，都做成了会失败的检查。
- **变异自检要成立有两个前提**：基线必须是绿的，变异必须真的改变行为。
  多次出现「测试写了但验不到点上」，都是变异自检发现的。
- **点名风险会让没被点名的地方无人复核。** 有一次两个人都逐行核了被点名的分支，
  而缺陷在旁边那条同类分支里。指出风险时，也扫一眼同形状的其它位置。
